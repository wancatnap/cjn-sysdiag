# 破烂优化

Windows 诊断与优化。全部在软件内完成，不调用系统自带的管理面板。

```
破烂优化.exe    64.3 MB   单文件，自带 .NET 运行时，双击即用
```

---

## 界面原则：不靠文字解释

三条规则，改 UI 时都按它判：

1. **卡片只有图标和名称。** 说明文字进 ToolTip（鼠标悬停才出现），不占版面。
   一条说明如果重要到必须常驻，那说明卡片本身没起对名字。
2. **页面只有标题和徽章。** 没有副标题。需要状态的地方用短词徽章（「只测不改」「不用重装」），
   需要确认的地方放进操作对话框——那时用户才会真的读。
3. **底部只有耗时和关闭。** 不放"提示"「免责声明」。它们会变成没人读的装饰。

**危险的说明去哪儿了**：不是删掉，是移位。涉及不可逆操作的警告（卸载预装应用、改 MSI、关停核）
放在**点击后的确认对话框**里，并写清可逆性与代价。常驻在页面里的警告，用户三天后就看不见了。

4. **公告没有按钮。** 只有标题和正文，不设「查看详情」也不设「关闭」。
   不需要关闭是因为它本来就不该长期占位——**显示过就算读过，下次启动不再出现**；
   不需要「查看详情」是因为正文已经把事说完，真要找功能，卡片区自己就有。
   这一轮把 23 处窗口副标题和 11 处权限说明也一起删了：前者是「每页一句自我介绍」，
   后者是在解释「以管理员身份重启」按钮为什么存在——按钮自己会说话。

**为什么这么砍对 DX/AX 也更好**：说明文字原来散在 18 个窗口的 `Subtitle` 和 16 个窗口的 `Note` 里，
每改一次功能就要同步改文案。现在副标题和底部说明的入口在控件层就已经去掉，编译器会拦住残留引用，
不存在"文档写了界面没写"的漂移。

## 怎么用

双击 `破烂优化.exe`。窗口里按 **9 个分组**排了 **75 张卡片**。

分组不按技术模块切，按**你想干什么**切——同一组里的卡片效果相近，找东西不用先想"它属于哪个子系统"。
顺序也是刻意的：先看（体检）→ 再清（腾空间）→ 再调（提速）→ 玩（游戏）→ 查（日志）→ 修（网络）→ 验（取证）→ 跳目录。

| 分组 | 内容 |
|---|---|
| **体检与硬件**（10） | 系统体检、磁盘健康（SMART）、系统信息（含精简判定）、已装更新、设备管理器（软件内）、显卡信息、磁盘管理（软件内）、设备安装记录、USB 设备清单、PnP 事件分析 |
| **清理与空间**（5） | C 盘清理、大文件管理（按大小找·删进回收站）、重复文件（按内容比对）、日志清理、注册表清理（只删孤儿项·10 类） |
| **系统优化**（10） | 系统优化（10 组 92 项，窗口内含「硬件调优」入口）、系统调优（Game Bar / GPU / 服务 / CPU 四档）、服务（可启停）、**服务预设**（批量禁用·可还原）、开机自启动、启动项、电源选项（高性能 / 卓越性能）、程序和功能（可卸载）、**免重装精简**（预装应用 / 遥测任务）、**优化推论**（23 条结论与依据） |

### 子窗口关闭时不会带走主界面

所有功能窗口都是主窗口的子窗口（`Owner`），关闭时做了两件事：

1. **延后一帧关闭**：点关闭的瞬间先不销毁窗口，等这次鼠标抬起事件处理完再关。否则窗口在鼠标抬起之前就消失了，同一次点击会穿透到下方的主窗口标题栏——如果正好落在「最小化」按钮上，主界面就自己最小化了（标题栏按钮位置跟窗口大小、DPI 有关，所以表现为"有时候"）。
2. **600ms 内兜底还原**：万一还是被最小化，自动还原回关闭前的状态（原来最大化仍是最大化），只触发一次。

两条都实测过：关闭子窗口后 120ms 强行最小化 → 自动弹回；关闭后 1.5 秒再最小化 → 保持最小化，不打扰正常操作。

## 日志分析：三种来源

游戏崩溃后拿到的东西形态各不相同，所以入口分三个，走同一套解析：

| 入口 | 适用 |
|---|---|
| **分析日志包** | 别人发来的 `.zip` |
| **分析日志目录** | 一个文件夹，进去后逐文件勾选 |
| **分析日志文件** | 直接多选 `.log` / `.txt` / `.evtx` |

解析层做三件事：

1. **识别编码与混淆**：UTF-8 / UTF-16 / GBK 自动判定；XOR 单字节密钥暴力还原（游戏日志常见）。
2. **归类**：按 `LogXxx: Level:` 这类前缀分类（Init / Net / Render / Audio / AI …），统计各级别条数。
3. **翻译**：把「Fatal / Error / Warning」翻成「崩在哪一步、要不要管、怎么处理」，而不是丢一堆原文。

实测：单文件 60 MB 量级、45 万行在秒级完成。报告落 `outputs/`，可在软件内直接打开。

## 取证：只读，且不靠猜

取证这一组共 17 张卡片，共同的底线是**全程只读**：不加载驱动、不注入、不 dump 内存——单文件绿色特性不能破。

### 精简系统上，本程序怎么表现

精简/魔改镜像会删掉 Defender 平台、Edge、WinRE、部分 WMI 提供程序连同服务键。
这些删掉之后，本程序里若干检测会**读不到数据**——这是最容易出事的地方：

> **读不到 ≠ 没问题。** 把「没检查成」当成「没有异常」，比报错更危险。

所以体检的第一步现在固定是「系统完整性」：先判定本机是不是精简系统，再往下查。
判定逻辑与「系统信息」里那套**共用同一个函数**（`DetectTrimmedOnly`），不会出现
「系统信息说精简、体检说完整」的自相矛盾。

在精简机器上，报告第一条会是这样：

```
本机是精简/魔改系统
缺失分 13，检查 25 项，缺 6 项：WinDefend 服务、OEM 制造商与型号、Edge 浏览器、产品名与内核版本…
构件被移除会让部分检测永远读不到数据——那不是权限问题，重装本软件也解决不了。
受影响的典型项：Defender 详细状态、网卡过滤驱动清点、部分 PCIe 属性、恢复环境相关。
```

各窗口的「读不到」也改成**说清原因**，而不是含糊的「无法判断」：

| 位置 | 原来 | 现在 |
|---|---|---|
| 防护状态审查 | 「读不到 Defender 详细状态」 | 追加「本机判定为精简系统，WinDefend 服务键已被移除——这是该接口读不到的原因，换管理员或重装本软件都无法改变」 |
| 外挂体检 · 网络过滤层 | 「MSFT_NetAdapterBinding 查询为空」 | 同样按缺失组件补归因 |
| 深度硬件痕迹 · PCIe | 「读不到链路信息」 | 同样补归因 |

**归因只给真正缺了的组件**：`AttributionFor` 传一个不存在的关键字必须返回空串，
自检里有一条断言守着这个。否则就成了「什么读不到都往精简上赖」，
那和「读不到就说没事」是同一种错——都是用一句话掩盖没查成。

**hosts 那 47 条是加速工具写的，不是精简系统留下的**：本机实测全部指向 `127.0.0.1`，
且集中在 GitHub（21 条）、Steam（13 条）、Greasyfork、YouTube、HuggingFace。
这是 Steam++/Watt Toolkit、FastGithub 一类工具的典型做法——先把域名钉回本地，
再由自己的代理去解析。现在会被识别成「符合加速工具特征」而不是「可疑的 hosts 改动」。

### 外挂痕迹体检

把分散的只读能力串成一条流水线（17 项采集、19 项检查清单），输出一份带姓名与机器特征码的报告。
和 pe-sieve / OpenArk 那类工具的区别在判定口径：

- 单项只算「提示」，多项组合才升「线索」
- **误报优先于漏报**：宁可少说，不把正常软件说成外挂
- 每个结论都带证据（路径 / 键值 / 事件 ID），不能只有一个分数

**报告由你选存哪儿**。点「报告」弹「另存为」，选好目录后**两个文件一起落在那里**：
`时间-外挂痕迹体检.html`（全文与证据）与 `时间-外挂痕迹体检.png`（结论长图）。
同名前缀让它们在资源管理器里紧挨着，不用再找。

> 之前的做法是直接写进 `outputs/`，图片单独命名成 `外挂体检-时间.png`——
> 中文名按拼音排序会排到列表最底部，实测有人翻不到，以为没生成。名字对齐就解决了。

**报告只保留最近 40 份**。每点一次「报告」都会新增文件，不加约束会越攒越多
（实测一个开发周期攒了 345 个）。现在每次生成报告后自动清理，只删本程序按
`时间-标题.html/.png` 模式生成的文件；你自己放进 `outputs` 的截图、图标、
`latency-experiments.json`、证据包 zip **不匹配这个模式，不会被碰**。
存到 `outputs` 以外的地方（U 盘、桌面）时**不做任何清理**。
自检里有三条断言守着这个边界。

**报告可以出图**。点「报告」一次同时生成两样：HTML 全文 + 一张 PNG 长图。
图是自己用 `DrawingVisual` 排的，不走浏览器——精简系统上 WebBrowser 常被移除，外部浏览器又抢不到前台。
图里是结论摘要（分数、分组、每条的标题与级别），正文与证据仍在 HTML 里。

**图上固定写明这段效力说明**，因为它会被单独转发、离开软件上下文后最容易被当成判定结论：

> 这份图能说明什么：一次只读扫描没有发现明显线索。
> 不能说明什么：没有线索不代表一定没开挂——DMA 设备、内核级实现、已被清理的痕迹、
> 以及跑在另一台机器上的方案，都可能不在本机留下可读的证据；反过来，部分线索也可能来自正常软件或精简系统。
> 所以它最多只能作为「大概率没开挂」的参考，不能当作判定依据。
> 复核请用同时生成的 HTML 报告，里面有每条结论的注册表路径、事件 ID 与文件路径。

这段文字是常量，自检有断言守着「必须含『大概率没开挂』与『不能当作判定依据』」，
防止以后改排版时顺手删掉。

**报告不再写「边界说明」段**（按需求移除）。报告头部固定六项信息：
填写者（窗口右上角输入）、机器特征码、机器名/用户名、开始时间、生成时间、耗时。

**机器特征码**：`SMBIOS UUID + 整机序列号 + 主板 + BIOS + ProcessorId + 磁盘 0` 的 SHA256 前 16 位，
格式 `XXXX-XXXX-XXXX-XXXX`。换内存条、加硬盘、改机器名都不变；读不到就显示「读不到」，不编假码。

#### 本轮新增的五项深度采集

| 采集 | 查什么 | 为什么能提精准度 |
|---|---|---|
| **服务与驱动来源** | `Services` 下全部驱动与服务的镜像路径 | 外挂的内核态落地必须注册驱动。只报两种**结构性异常**：镜像在临时/下载/回收站目录、系统目录下登记了但文件已不存在 |
| **无文件持久化** | WMI 事件订阅 / `AppInit_DLLs` / IFEO 映像劫持 | 这三处能让外挂在重启后继续生效，却不出现在任何启动项列表里。正常系统里通常为空 |
| **隐藏进程比对** | Toolhelp32 / PSAPI / WMI 三套枚举的 PID 差集 | 外挂会 hook 进程枚举让自己从任务管理器消失；三套机制同时说谎很难 |
| **文件行为特征** | Temp / 下载 / 公共目录里最近可执行文件的**导入表** | 读写他人内存、远程线程注入、全局键盘钩子——这些能力必须导入对应系统函数。看能力比看文件名可靠 |
| **网络过滤层** | 网卡上绑定的 WFP / NDIS 轻量过滤组件 | 挂在内核网络栈上的驱动能看、也能改进出数据包。VPN、杀软、虚拟机都装，所以只清点不下结论 |
| **网络隐蔽手法** | hosts 自定义映射、系统代理/PAC、npcap/WinPcap、DNS 是否指向非网关非公共地址 | 这四样**改一行配置就能生效**，不装驱动、不碰游戏进程，比写 WFP 驱动门槛低得多 |

#### 网络层：越隐蔽的手法，越靠「你认不认得」

WFP / NDIS 过滤驱动要写驱动、要签名、要过反作弊的驱动枚举，门槛高。
真正低门槛且隐蔽的是另外四样——它们共同点是**游戏进程完全不受影响，本机也留不下执行痕迹**：

| 手法 | 能做什么 | 判据与误报来源 |
|---|---|---|
| **hosts 劫持** | 把厂商登录/心跳域名指到别处，或指到回环让它连不上；先于 DNS 生效 | 指向**具体 IP** 的比指向 `0.0.0.0` 的可疑得多——后者通常是广告屏蔽脚本干的，所以两者级别不同 |
| **系统代理 / PAC** | 明文请求经中转，中转方能看到也能改写响应 | 公司网络、加速器、翻墙软件都会设，只能列为提示 |
| **抓包驱动**（npcap/WinPcap） | 普通程序即可读到全部进出网卡的数据包，是「外部雷达」的前置条件 | 装 Wireshark 就会带上，所以这是「具备条件」不是「在作弊」 |
| **自建 DNS** | 效果同 hosts，但本机看不出任何域名映射痕迹 | 与 hosts 互补：hosts 查不到时它可能是答案。公司内网 DNS 会落进这一档 |

**本机实测**：这台机器的 hosts 里有 47 条自定义映射，全部指向 `0.0.0.0`/`127.0.0.1`
（典型的广告/遥测屏蔽），所以报的是「提示」而不是「线索」。这正是判据分级的用处——
同样是「hosts 被改了」，指向回环和指向某个真实 IP 是两件事。

**这四项全是提示级**，没有一项能单独定性。判断办法只有一个：名字能不能对上你装过的软件。


**这三项都返工过，原因值得记**：

1. 驱动签名最初用 `X509Certificate.CreateFromSignedFile` 判断，本机跑出 **206 条假异常**——
   `AcpiDev`、`acpipagr`、`1394ohci` 这些系统自带驱动全被判「未签名」（该 API 解析不了嵌入式签名的 .sys），
   ACE 反作弊装在 Program Files 的驱动被判「不在系统目录」（我当时的可信目录只认 System32）。
   **现在完全去掉签名判定**，只保留两条可靠判据。自检里有断言守着「正常系统上镜像异常 ≤ 3 条」。
2. WMI 订阅最初「有订阅 = 线索」，但 Windows 自带一条 `SCM Event Log Filter`
   （服务控制管理器把服务启停写进事件日志），几乎每台机器都有。已列白名单，只报第三方订阅。
3. `AppInit_DLLs` 默认值就是空且 `LoadAppInit_DLLs=0`，必须两个条件同时成立才报，
   否则「键存在」本身会被误判。

修完之后本机风险分从 **100（高）→ 11（低）**，线索从 13 条 → 0 条。

#### DMA 与「伪装过的 DMA」

DMA 外挂（PCILeech / LeetDMA 一类）用一块 FPGA 板插在 PCIe 或雷电口上，由硬件直接读物理内存，
**完全绕过进程与 API Hook**。游戏进程本身干干净净，所以任何进程内检测都抓不到它。

更难的是**伪装**：高级固件会把厂商 ID、设备 ID、类代码全改成一块真实网卡，
于是「查 Xilinx 0x10EE」这种清单式检测直接失效。公开资料（Clubhouse AC 的 PCIe 指纹研究、
`gmh5225/awesome-game-security` 的 DMA 章节、PCILeech 生态）给出的完整判据分三档：

| 档位 | 判据 | 本程序 |
|---|---|---|
| **配置空间** | 能力链完整性、BAR mask 尺寸、保留字节非零、Xilinx IP 残留字节、DSN 能力出现性 | **不做**。全部要内核态读配置空间 |
| **行为** | 链路宽度/速率与宣称矛盾、BAR 读回的寄存器内容、MSI 是否真的产生中断、完成延迟分布 | **做前两条里的「链路矛盾」**；后两条要发 TLP，做不到 |
| **平台** | IOMMU 是否真在重映射、设备是否落在重映射域内、VBS 是否拦住 BYOVD 关表 | **做**（读 Windows 自己的策略，不解析固件表） |

**本程序实际用的四条判据（都在用户态可验证）**：

| 判据 | 为什么可靠 |
|---|---|
| **同一 VID/DID 对应了不同设备类** | 同一颗芯片的类代码是固定的。这是逻辑矛盾，不是概率判断——伪装固件只改 ID 忘改类代码时必犯 |
| **网卡声称 x8/x16 链路** | 真实消费级网卡最高 x1，100G 双口才到 x8。FPGA 直接把 x8/x16 链路能力报上来 |
| **显卡只有 x1 链路宽度** | 显卡空闲时降的是**速率**不是**宽度**。宽度掉到 x1 一般是转接卡或非显卡设备 |
| **厂商与设备类不匹配** | Realtek 不做显示控制器，NVIDIA 不做存储控制器。矩阵只收产品谱系窄的厂商——**刻意不收 Intel/AMD**，它们什么类都做，收进去只会误报（本机实测就误报过一条） |

**三条边界，界面上都写着**：

1. **不解析配置空间**：能力链、BAR 尺寸、DSN 能力、保留字节都读不到。伪装得好的固件能过这里所有检查。
2. **「没查到 FPGA」不等于没有**：伪装过的 DMA 板在设备管理器里就是一块网卡。
3. **平台策略 ≠ 保护已生效**：`DmaSecurity` 里没有放行任何总线，只说明 Windows 没被配置成关保护；
   重映射是否真在跑还取决于固件 opt-in 与 BIOS 里 VT-d / AMD-Vi 是否启用，这两项用户态读不到。
   有公开 PoC（DieDMAProtection）演示从内核驱动运行时关掉重映射，所以「策略正常」不能当绝对保护。

**这一轮改掉了一个真错误（值得记下来）**：上一版用 ACPI 的 `DMAR` 表 flags 判断 DMA 保护，
两处都错了——`GetSystemFirmwareTable` 的 provider 常量写成了 `0x52534D42`（"BMSR"），
正确的 ACPI 是 `0x41435049`，所以这个调用**永远返回空**，界面上一直显示「读不到固件表」；
而且 DMAR flags 的 bit0 是中断重映射，bit2 才是 DMA 保护 opt-in，即便读到了方向也是错的。
现在改成读 `HKLM\SYSTEM\CurrentControlSet\Control\DmaSecurity` 的 Windows 实际策略，
并用「策略层没有放开」这种不越界的措辞——不再声称「保护已启用」。

排错入口：`破烂优化.exe --dma-probe`（打印每个设备读到的链路/类代码与全部判定）、
`--dma-keys <实例关键字>`（列出该设备所有 PCI 属性编号与值，用来核对属性键有没有错位）。

> 属性编号是**在本机反推出来的**：最初按记忆写的 12/13/14/15/17/18/20 全部读成 -1，
> 界面上表现为「所有设备都读不到链路」。差一点就把「读不到」当成「没有异常」报出去——
> 用空白冒充结论，比报错更危险。现在的编号（3/4/9/10/11/12/13）是靠
> 「pid=16 读出 513 = 系统工具报的 BarTypes」这类交叉验证反推的，自检里有断言守着数据自洽。

### 机器码与机器码伪造检测

- **机器码**：`SMBIOS UUID` + 整机序列号 + 主板序列号 + BIOS 序列号 + ProcessorId + 磁盘 0，登记后做一致性校验（首次登记 / 一致 / 部分变化 / 核心全变）。

## 清理：三块，都先给你看清单

### C 盘清理

扫描阶段**完全只读**，清理阶段逐项执行，默认「安全项直接删、谨慎项进回收站」。
不做静默删除——必须先拿到用户的勾选结果。

规则库解析 `Winapp2.ini` 格式：支持层级通配、`%ProgramFiles%` 等变量、`Category` / `LangSecRef` 分组。
`Program Files` 下只放开 Steam 的四个缓存根，其余一律不碰。

### 注册表清理

**只删孤儿项**，不碰任何「可能有用」的键。判断依据只有一条：**登记的东西确实不在磁盘上**。

- `Run` / `RunOnce`（含 `WOW6432Node`）里指向已不存在文件的项
- `Uninstall` 里卸载命令已失效的项
- `App Paths`、`SharedDLLs`、`MuiCache` 的失效条目
- **字体** —— `Fonts` 键里登记的字形文件已不在 Fonts 目录
- **帮助文档** —— 旧 `.hlp/.chm` 登记指向的文件已删除
- **服务映像** —— 服务的 `ImagePath` 指向的 exe/sys 不存在（这种服务本来就起不来）
- **声音事件** —— 声音方案里的事件 wav 已被删
- **防火墙规则** —— 规则绑定的程序路径已不存在

每个键在 `reg export` 逐键备份之后才动，默认**全不勾**。

**刻意不做的三类**（Wise 一类工具有，这里明确放弃）：

| 类别 | 为什么不做 |
|---|---|
| COM 组件（`CLSID\InprocServer32`） | 大量 CLSID 是延迟注册的，DLL 不在不代表无效，误删会让程序装不上 |
| 文件扩展名关联 | UWP / WinRT 的 `.xxx → ProgID` 大量动态生成，静态判断误报率太高 |
| 映像劫持（IFEO） | 那是**安全信号**不是垃圾数据，删掉等于毁证据；交给取证模块报 |

### 大文件管理

「清理与空间」→ **大文件管理**。按大小把磁盘上占地方的文件列出来，**只找不改**。

- 可选扫描范围（默认所有固定盘），阈值 100 MB ~ 10 GB
- 系统目录（Windows / Program Files / ProgramData）不进入——拖慢扫描，也避免误删
- 列：文件名、大小、类型（视频/镜像/压缩包/安装包/游戏资源/转储）、最后访问、所在目录
- 双击一行直接在资源管理器里定位该文件
- 删除**一律进回收站**，可还原；被占用的文件会跳过并如实报告

> **为什么不做「一键推荐清理」**：20 GB 的游戏安装包和 20 GB 的工程素材在程序眼里一模一样，
> 价值却天差地别。这个窗口的定位是**帮你找到它**，不是**替你做决定**。

### 重复文件：三级流水线，只删到回收站

「清理与空间」→ **重复文件**。算法照 Czkawka 的思路做成三级流水线，把最贵的全量哈希留到最后：

| 级别 | 做什么 | 代价 |
|---|---|---|
| 1. 按大小分组 | 大小不同的文件绝不可能重复，纯内存操作 | 0 |
| 2. 预哈希 | 同尺寸的文件只读**头 4KB + 尾 4KB**，指纹不同就不再往下走 | 8 KB IO |
| 3. 全量哈希 | 只有前两关都活下来的才完整读一遍（SHA256） | 整份文件 IO |

本机用小样本实测：6 个文件里 3 个同尺寸，预哈希把内容不同的那个挡掉，真正全量比对的只有 2 个。
自检把这条固化成断言——如果哪天预哈希失效，`深比对` 的数字会从 2 变成 3，断言立刻失败。

**为什么只做重复文件，不做相似图片/相似视频**：重复文件是**字节完全相同**，判错的概率在工程上等于零，
这是敢让用户删的前提。相似图片靠感知哈希，误判的代价是「用户把自己不同角度的照片当重复删了」——
这个风险不值得为了多一个功能去承担。

**交互上刻意慢半拍**：扫描完**不自动勾选**任何文件；要用户先点「每组只留最早的」（这一步会勾上每组除最早之外的所有副本），
再点「删除选中」，确认框里再报一次文件数和总大小。删除只走回收站，没有永久删除。

**明确的限制**：不识别硬链接（两个硬链接指向同一数据块，会被当成两份重复）；不做跨盘符去重；
跳过 `Windows` / `Program Files` / `AppData` / `node_modules` / `$Recycle.Bin` 等目录；
不缓存哈希，所以每次扫描都要重读候选文件（省掉的是全量读，不是全部 IO）。

### 日志清理

可逐文件勾选，删前显示大小与最后修改时间；正在被占用的文件会跳过并说明。

| 问题 | 判据 |
|---|---|
| 元素越界 | 相对根元素的矩形超出右/下边界 1.5px 以上（滚动区内的元素豁免，那是它的职责） |

   改成 WrapPanel 自动换行。

   先试了 WrapPanel，但两组换行点不一致，「原始」和「应用后」就错位——而这块的全部意义就是逐块对比，
   最终改成固定 6 列 UniformGrid。
3. **小屏适配**：三分之二窗口的 Height 在 780~900，1366×768 笔记本工作区只有约 728。WPF 不会自动把窗口
   缩回屏幕，底部按钮会被切掉且点不到。现在统一在窗口加载时压到工作区高度内（一处 hook 覆盖全部窗口）。

## 九类系统工具：全部搬进软件内

设备管理器、服务、电源选项、可靠性监视器、程序和功能、磁盘管理、显卡信息、任务管理器、防火墙——这些原本都要开系统自带工具，现在都做成了软件内的页面。

**共用一套骨架**（`ToolPage` + `ToolListWindow`）：页头 + KPI + 工具条 + 表格 + 选中行详情条 + 右键菜单 + 自动刷新 + 提权重启。九类工具只是数据源不同。

几个实测出来的细节：

- **服务**：326 个 Win32 服务里有 24 个是「按用户」模板（`cbdhsvc` / `OneSyncSvc`），单独标成「按用户启动」，否则 KPI 和筛选标签对不上（195 vs 219）。
- **服务方向**：点「开启它」如果反而把 `WSearch` 恢复自启就是反了。现在 `onStart=4`（禁用）/ `offStart=3`（手动），文案改成「已生效 / 未生效」。
- **电源**：直接读 `powrprof.dll`，不调 `powercfg.exe`——精简镜像里 System32 的 exe 被删得很随意。高性能方案不存在时现场复制一份。
- **可靠性**：`Win32_ReliabilityStabilityMetrics` 的指数 0~10，和系统面板同源。
- **卸载命令**：`"C:\Program Files\App\uninst.exe" /S` 这种带引号的要正确拆分（`ParseCommand`），否则路径带空格就废。
- **关键进程**：`lsass` / `csrss` 这类拒绝结束，不是弹错误，是直接不允许点。

### Atlas 参考：只挑「运行时就做得了」的那部分

AtlasOS 的 playbook 里 `tweaks/` 目录确实有大量注册表项。但它整套方案有个前提：**全新安装**——
很多效果来自改镜像、删组件，不重装拿不到。所以这里只挑符合三个条件的：

1. Atlas 的 `src/playbook/Configuration/tweaks/` 里确实有这一项（不是我编的）；
2. 能用「一个键 + 一个值」静态表达，不需要跑脚本、不需要改镜像；
3. 写入前能记下原值、随时能还原。

最后收了 6 项：

| 项 | Atlas 里的位置 | 代价（这是我加的，Atlas 不写） |
|---|---|---|
| `DisablePagingExecutive` | performance | 少几十到一百多 MB 可用内存；8GB 以下机器收益不明显 |
| 解除 SMB 带宽限制 | 网络 tweaks（`LanmanServer` + `LanmanWorkstation`） | SMB 不再给其他程序让路，边玩游戏边走网络盘可能抢带宽 |
| 关 LLMNR（`EnableMulticast=0`） | 网络/安全 tweaks | 同网段按主机名互访的老设备会找不到，得改用 IP |
| `AutoEndTasks=1` | Qol 脚本 | **会丢数据**：未保存的文档被直接结束，没有确认机会 |
| `LargeSystemCache` | performance | 对游戏收益不明确，缓存挤占应用内存；建议当单变量实验做 |
| `NoNetCrawling` | explorer tweaks | 网络位置不再自动列出，访问共享要手输地址 |

**没收进来的**（以及为什么）：依赖具体硬件的（蓝牙、触摸板节能）、改安装介质的、
删 WinSxS 组件的、移除 Edge/Defender 的——这些在「免重装精简」里单独说明，只讲边界、不给按钮。

**`AutoEndTasks` 那条标的是「谨慎」，不是「安全」**：自检里有一条断言专门守它——
凡是代价里写了「丢」的条目，不允许出现在安全档。因为界面上有「全选安全项」按钮，
一旦它被误标成安全，用户点一次就会在不知情的情况下接受「关机丢文档」。

- **三档风险**：安全 / 谨慎 / 不推荐，默认只勾安全项
- **写前记原值**：`tweaks-backup.json`，每项都能单独还原
- **可导出**：`.reg`（根键写全名，否则导入会失败）+ `.cmd`
- **双向**：每项都验证过「开 → 关 → 还原」三步，不是只能开不能关
- **会丢数据的项不会被算成「安全」**：自检里有一条断言专门守这个——
  「缩短关机等待」「自动结束无响应程序」这类会导致未保存内容丢失的，必须是「谨慎」档

**没做的**：网卡级参数（`*RSS`、`TcpAckFrequency`）需要按接口 GUID 逐个写，
静态清单表达不了；这一块留给「网络」窗口按实际网卡处理。

## 性能与进程

任务管理器 / 资源监视器 / 性能监视器是**同一套实时视图**（`MonitorService`），只是默认排序和列不同。

- CPU 占用用**两次采样求差**，不是读瞬时值
- 列表用虚拟化，只建 6 个容器（实测内存可控）
- 采样开销：4 次采样平均 20 ms，单次分配 < 2 MB
- 单进程私有内存 < 200 MB，闲时自动回收工作集

### 内存：先看清，再决定要不要动

「性能与进程」→ **内存**。这个窗口不做「一键加速」那套——
Windows 里待机列表（standby）本身就是缓存，占着物理内存但随时可以让出来，清空它只会让下一次读盘变多。
所以只做两件事：看清谁在占内存，以及在知道代价之后执行两个动作。

**读数来自三路，互相独立**：某一环读不到只让对应字段显示「读不到」，不影响其他部分（精简系统上经常只缺其中一路）。

| 来源 | 拿到什么 |
|---|---|
| `GlobalMemoryStatusEx` | 物理总量、可用、页面文件总量 |
| `GetPerformanceInfo` | 已提交 / 上限、系统缓存、分页与非分页池 |
| `NtQuerySystemInformation(SystemMemoryListInformation)` | 待机、已修改、空闲——按页列表的优先级桶求和 |

顶部四段构成条（进程与内核 / 已修改 / 待机 / 空闲）加起来必须等于物理总量，自检守着这条；本机实测差 **0.0%**。

**两个动作，代价写在确认框里而不是藏起来**：

| 动作 | 真实效果 | 代价 |
|---|---|---|
| **清理待机列表** | 已用真正下降，可用物理内存立刻变大。这是用户态唯一能腾出物理内存的动作 | 缓存页下次要用得重新从磁盘读，接下来一段时间打开程序变慢；SysMain 会慢慢把缓存建回来。**不减少任何提交量** |
| **回收选中进程工作集** | 基本只改数字：页被挪进待机列表，进程下次访问立刻换回 | 物理内存几乎不变；对关键进程调用会引起大面积缺页，所以 System / dwm / csrss / lsass 等直接禁止勾选 |

第二个动作的确认框原话是「这一步基本只改数字」。不这样写，用户会以为任务管理器数字变小就等于优化成功。

**两个实测踩到的坑（都写进代码注释了）**：

1. `PERFORMANCE_INFORMATION` 里 `CommitTotal` / `CommitLimit` / `SystemCache` / `KernelPaged` / `KernelNonpaged`
   的单位是**页**，不是字节。少乘一次页大小，提交量会显示成 5.9 MB（实际 22.6 GB）。
2. 待机页**属于「可用」，不属于「已用」**。把待机再从已用里减一次，会算出比所有进程工作集之和还小的假数字
   （本机 225 个进程加起来 10 GB 级，错误公式给出 2.6 GB）。现在的口径是「进程与内核 = 已用 − 已修改页」。

**直播伴侣优化会顺带清一次待机列表**：编码器要连续物理页，这是那一轮里唯一真能腾出物理内存的动作。
不做工作集回收——那反而让直播软件下次采集时缺页。还原时明确写「内存动作是一次性的，没有可还原的设置」，
免得用户以为漏做了什么。

排错入口：`破烂优化.exe --mem-probe` 打印三路原始值、四段合计校验和前 12 个进程（只读）；
加 `--purge` 才真的清一次待机列表，用来核对「清完到底有没有变化」（需管理员）。

**直播伴侣优化**：降优先级 + 限核心 + 高性能电源，外加这一轮按 OBS 官方编码指南与社区排查清单补的四项。

核心掩码 `0xFE` / `0xE` / `0x1` 三档（避开 CPU 0 / 避开前三个核 / 只用第一个核）。

新增的四个系统层设置：

| 项 | 做什么 | 为什么 |
|---|---|---|
| **GPU 图形首选项** | 给直播软件的 exe 单独设 `GpuPreference=2`（高性能） | Windows 会把「后台」程序的 GPU 调度降级，画布合成可能被丢到核显，编码器吃不到独显。只对这一个 exe 生效，HKCU 免管理员 |
| **MMCSS 捕获任务** | `Tasks\Capture` 的 Priority 8→6、Scheduling Category → High、SFIO → High | 直播软件注册采集线程时用这组配置。改了能让采集在游戏满载时更稳地拿时间片，代价是更用力抢 CPU |
| **HAGS 状态** | 只读显示，不自动改 | 硬件加速 GPU 调度与部分采集/编码组合有冲突（预览卡、编码延迟抖），但它同时影响游戏帧率。**是不是该关取决于卡和驱动版本，只能自己实测对比**，所以不替用户决定 |
| **覆盖层冲突** | 只读列出 Discord / GeForce / RTSS / Steam / GameBar 进程 | 多个覆盖层同时挂钩捕获是「游戏里流畅、直播画面却卡」的常见原因 |

改前留底：GPU 首选项只改 HKCU 里那一个值，还原时按分号拆分、只剥掉 `GpuPreference=` 字段，
保留同一行里的其他设置；MMCSS 的原值写进 `outputs/live-capture-backup.json`，还原时按原值写回。

**本地实测**：这套机器上 HAGS 已开启、游戏模式关闭、GeForce 覆盖层在跑——
正好是「直播画面卡但游戏不卡」的典型配置，窗口一打开就能看到。

**系统调优 / 硬件调优**：Game Bar、GPU 调度、SysMain、CPU 四档性能、鼠标精准输入，每项都能还原（含 SysMain 的启动类型）。
「系统优化」组里有独立卡片，主界面直接可见；「系统优化」窗口右上角也留了「硬件调优」按钮作为第二入口。
没并进那 92 项开关清单，是因为 CPU 四档是下拉选择、服务是批量禁用，逐项布尔开关的模型表达不了，硬合会丢功能。

## 显示器配色（ICC）：套配置 + 导入导出

「游戏与显示」→ **显示器配色**。对标 码枪堂 的「色彩去曝光」，只做**能验证**的那部分。

### 一、为什么「套了 ICC 没效果」——实测出来的根因

先说结论：**关联 ICC 和「画面变样」是两件不同的事**，早期版本只做了前者，所以看起来没反应。

用 `--icc-probe` 探针在本机（HKC2441，精简系统）逐环测出来的：

1. **ICC 的矩阵 / 曲线只是「色彩描述」，桌面和游戏根本不读。**
   Photoshop、部分浏览器、打印预览会读；桌面合成、全屏游戏、视频播放器不读。
   所以「关联成功但观感不变」是 ICC 机制的正常表现，不是没生效。
2. **真正改变屏幕输出的是 ICC 里的 `vcgt` 标签**（Video Card Gamma Table）。
   校准软件（Windows 校准、DisplayCAL）把校准结果写成这张 RGB 查找表，由系统通过
   `SetDeviceGammaRamp` 写进显卡 LUT——**这一步才肉眼可见**。
3. **实测：系统从来没帮我们加载过它。** 套了配置之后读显卡 LUT，仍是完全线性的
   `0 / 16448 / 32896 / 49344 / 65535`（即 `i × 257`）。Windows 只在登录等时机按**系统级**关联加载，
   per-user 关联 + 绝对路径这条路它不管。
4. **厂商官网下的 .icm 大多不含 vcgt**，只有色域描述——这类文件套上去本来就不该有变化。
   本机 6 个配置里刚好 3 个含校准表（偏差 20~25%），3 个不含。
5. **关联值必须写文件名，不能写完整路径。** 系统按文件名去 `color` 目录找，早期版本一律写绝对路径，
   结果是「键写进去了、系统解析不到」。现在：在系统目录 → 写文件名；在别处 → 写完整路径。
6. **`GetICMProfile` 只反映系统级关联**，看不到 per-user 设置；而且它必须用
   `CreateDC("DISPLAY", 设备名, …)` 打开 DC，把设备名当驱动名传进去也能拿到 DC，
   但读出来永远是 sRGB（早期版本踩过这个坑）。
7. 系统自己的接口是 `mscms.dll!WcsSetDefaultColorProfile`（Win8+，「设置 → 显示 → 颜色配置文件」背后就是它）。
   返回 `S_FALSE(1)` 表示「已经是它、没改动」，不是失败；它按**追加**语义改清单，
   所以两边必须用同一个名字，否则列表会越加越长。

### 二、能做什么

| 动作 | 说明 | 权限 |
|---|---|---|
| 列出显示器与当前配置 | `EnumDisplayDevices` + `GetICMProfile`（系统级），型号从 EDID 读 | 不需要 |
| 列出所有 ICC | 系统 color 目录 + 本程序目录，解析描述/色彩空间/版本/gamma，**并标出含不含校准表、偏差多少** | 不需要 |
| **应用所选** | 写 HKCU 关联 + 调系统 API + 强制重读，**再把校准表写进显卡 LUT** | 不需要 |
| **只重写 LUT** | 不动关联，只重写显卡 LUT（带强度 0~100%） | 不需要 |
| **还原 LUT** | 写回第一次改动前存的原始 LUT | 不需要 |
| 恢复默认 | 关联与 LUT 一起还原（`icc-backup.json` + `icc-lut-backup.json`） | 不需要 |
| **导入 ICC** | 有管理员 → 装进系统 color 目录；没有 → 放本程序目录（用绝对路径） | 视情况 |
| **导出 ICC** | 原样复制到任意位置，不动系统设置 | 不需要 |
| 命令行还原 | `--icc-restore`：画面被改坏、界面进不去时的退路 | 不需要 |
| 诊断探针 | `--icc-probe`（只读）／`--icc-probe --live`（真写一次再还原） | 不需要 |

### 三、显卡 LUT 的三个细节

1. **强度混合**：以「第一次改动前的原始 LUT」为基线线性插值，不是叠在上一次结果上，
   所以反复拖强度不会累积失真。
2. **写完回读校验**：`SetDeviceGammaRamp` 返回 true 也可能被驱动静默忽略。
   每次写完都把 LUT 读回来比对，差值 > 3000/65535 就如实报「驱动没接受」。
3. **重启会丢**：系统不会替我们保持。勾「下次启动时自动重新应用」，程序启动时静默重放一次
   （`icc-lut-state.json` 记录哪台屏套了哪个配置、什么强度）。

### 四、什么时候仍然看不到变化

- 显示器开着 **HDR**：系统接管 LUT，写入会被忽略（程序会提示）。
- 显卡驱动接管了色彩（N 卡「数字振动」、A 卡「自定义颜色」）：先把驱动那套恢复默认。
- 配置本身不含 vcgt 且曲线贴近线性：偏差 < 1.5% 时肉眼基本看不出，程序会直说。
  这时可以勾「按色调曲线合成」强行取它的 gamma 做近似——但那是近似，不等于原厂校准。

### 五、边界

- **不是校色**：没有色度计，改的是「系统按什么配置去换算」，不是「把这块屏调到准确」。
- **色彩关联只影响走 Windows 颜色系统的程序**；要「整个桌面都变」必须靠显卡 LUT。
- **HDR 下 LUT 无效**，这是系统限制，不是程序问题。

## 手动调色：gamma / 亮度 / 对比度 / RGB 增益

「游戏与显示」→ **显示器配色** → 左下角 **「手动调色…」**（或命令行 `--open-color-tune`）。

不依赖任何 ICC 文件，直接按参数生成 LUT 写进显卡——**拖动滑块，整块屏幕立刻变**（含全屏游戏，HDR 除外）。

### 一、六个参数怎么算

顺序固定，改顺序观感就会变，所以写死：

```
输入 x = i/255
  → x = pow(x, 1/gamma)              中间调：gamma 越大越亮
  → x = (x - 0.5) * contrast + 0.5   对比度：以中灰为轴，暗更暗、亮更亮
  → x = x + brightness/100           亮度：整体偏移，抬黑位能让暗部浮出来
  → x = x * gain[ch]                 通道增益：调白平衡 / 冷暖
  → clamp → ×65535
```

| 参数 | 范围 | 中性值 | 说明 |
|---|---|---|---|
| Gamma | 0.40 ~ 3.00 | 1.00 | 中间调亮度。大于 1 抬暗部 |
| 亮度 | -50 ~ +50 | 0 | 整体偏移。抬黑位代价是纯黑变灰 |
| 对比度 | 0.50 ~ 2.00 | 1.00 | 以中灰为轴拉开/压紧 |
| R / G / B 增益 | 0.50 ~ 2.00 | 1.00 | 分通道缩放，调冷暖与白平衡 |

**中性值一定生成完全线性的 LUT**（自检守着：`i*257` 逐项相等），所以「参数相同 → 结果一定相同」，不会因为操作顺序漂移。

### 二、为什么是「绝对 LUT」而不是叠加

每次写入都用当前参数重新生成整条 LUT，不在上一次结果上累加。这样：

- 拖回中性值 = 精确复原，不会残留
- 参数和效果一一对应，可存、可重放、可导出

### 三、实时写入的取舍

`SetDeviceGammaRamp` 本身很快，但拖滑块时每帧都写会让整个桌面（包括本窗口）闪烁。
所以加了 **80ms 节流**：跟手，又不闪。关掉「实时预览」后只有点「应用」才写入。

写入后**一定回读校验**（差 > 3000/65535 判驱动没接受），和 ICC 那条链路用的是同一套。

### 四、分屏对比：拿一张真实画面来回划

右侧对比区把**同一张画放两遍**：底层是原始像素，上层是过完 LUT 的像素，再用 `Clip` 只露出竖线**右侧**。

- 左边 = 原始，右边 = 调整后（和上方的标注一致）
- 拖动竖线：往左拖看更多原始，往右拖看更多调整后；拖到两头就是全幅
- 缩放窗口时按比例保持分割位置

> **为什么建议用实拍画面**：色卡只能对比孤立颜色，看不出**过渡**和**真实场景**。
> 一张游戏截图里同时有天空、阴影、草地、金属、人物肤色——暗部有没有压死、高光会不会溢出、
> 整体偏冷还是偏暖，一眼就能判断。这也是当初要这个功能的初衷：调完要能立刻判断"游戏里会不会更清楚"。

**底图要自己选，程序不内置任何图片。** 这既是合规要求（游戏截图、摄影作品都有版权，
不能随源码分发），也让你能挑自己最关心的那张画面：

- 点右上角 **「换底图…」** 选任意 jpg / png / bmp / tif，长边超过 1920 会自动等比缩放
- 存到 `%LOCALAPPDATA%\SysDiag\color-reference.jpg`，下次打开直接命中
- 点 **「用色卡」** 删掉自定义图，回到程序化生成的灰阶 + RGB 渐变 + 色块
- 什么都不选时用色卡兜底——不会因为缺一张图让面板打不开

### 五、这一层是怎么算的

不是给 WPF 套滤镜，是**真的逐像素跑 LUT**：把底图转成 `Bgra32` 字节数组，
每个通道用 256 项字节表查一次（`byte = ramp[ch*256 + value] >> 8`），再写进 `WriteableBitmap`。

- 1920×1080 的底图约 200 万像素，一次 **8~15 ms**，拖滑块跟手
- 复用同一个 `WriteableBitmap` 和同一块缓冲，不反复分配（否则 GC 一直响）
- 底图只加载一次，失败也记住，不会每次拖动都去碰磁盘

通道顺序（B/G/R）有断言钉住：`只压 R 通道时 B/G/A 必须纹丝不动`。
这个不测的话，接错位会让人像发蓝、草地发红，而画面看着"只是有点怪"，很难归因。

### 六、导出成 ICC：这是真文件，不是改后缀

`IccWriter` 按 ICC.1:2001-04 逐字节生成，不是拼一个空壳：

```
128 字节头 + 4 字节标签数 + N×12 标签表 + 标签数据（每条 4 字节对齐）
```

标签：`desc` / `cprt` / `wtpt`(D50) / `rXYZ·gXYZ·bXYZ`(sRGB 色域矩阵) / `rTRC·gTRC·bTRC` / `vcgt`

**分工必须说清**：TRC 只能表达 **gamma**；亮度、对比度、RGB 增益全部落在 **vcgt** 里。
所以别的软件打开这个文件，看到的 gamma 是对的，但看不到完整调整——
只有真正加载 vcgt 的路径（Windows 校准加载器、本程序的「应用配置」）才有完整效果。

实测验证（`--tune-icc-probe`）：

```
解析：valid=True　desc=SysDiag Probe　space=RGB　v=2.2　gamma=1.30
vcgt：表格型 3×256 项
往返：最大差 0/65535（内存 LUT 与文件里的表逐项一致）
系统色彩管理：已接受（WPF ColorContext 打开成功）
```

最后一条最关键——用系统自己的色彩管理打开，结构不合法会直接抛异常。

### 七、边界

- **不是校色**：没有色度计，这套只调显卡 LUT，效果类似显示器 OSD 的 gamma/对比度。不含色域映射。
- **HDR 下无效**：系统接管 LUT，写入会被忽略（程序会提示）。
- **关窗口会问一次**：调完直接关，屏幕会一直留着那个色调。非中性且有实际写入时弹「保留 / 还原 / 取消」。

## 延迟优化（时钟 / MSI / 外设节能 / 计时器 / 虚拟化 / 电源与显卡）

「游戏与显示」→ **延迟优化**。对应 码枪堂 的延迟页，实现全部自己写，**读不到就说读不到**。

### 一、六组检查

| 检查项 | 怎么读 | 能不能改 |
|---|---|---|
| 平台时钟 `useplatformclock` | `bcdedit /enum {current}` | **两种模式二选一**（见下），需管理员 + 重启 |
| 动态滴答 `disabledynamictick` | 同上 | 能改，需重启 |
| GPU / 网卡 MSI 中断 | `Enum\...\Interrupt Management\MessageSignaledInterruptProperties\MSISupported` | 能改（需管理员 + 重启） |
| USB 选择性暂停 | `PowerReadACValueIndex`（子组 `2a737441…`、设置 `48e6b7a6…`） | 能改（`PowerWrite` + 重新激活方案） |
| HID「允许关闭以省电」 | `Enum\HID\*\Device Parameters\SelectiveSuspendEnabled` | 能改（需管理员） |
| 计时器分辨率 | `NtQueryTimerResolution` | **只读**：本程序不常驻，锁不住 |
| **Hyper-V** `hypervisorlaunchtype` | `bcdedit` + WMI `HypervisorPresent` + DeviceGuard 注册表 | **能开能关**，需管理员 + 重启 |
| **卓越性能电源** | `PowerEnumerate` + 注册表扫描（见下） | 能创建 / 切换 / 切回，**不需要管理员** |
| **游戏进程优先级** | `GameProcessCatalog` 认出正在跑的游戏 | 能改（退出游戏自动恢复，不写注册表） |
| **N 卡最高 Boost** | WMI 显卡名 + 驱动版本 | **只生成 .nip**，不直接写驱动库 |

本机实测：计时器 `0.600 ms`（系统最小 `0.500`）、GPU 3 个设备里 2 个已开 MSI、USB 选择性暂停已禁用、HID 64 个设备 0 个省电。

### 二、HPET 是「两种模式」，不是单向开关

`useplatformclock` 有三种状态，程序给两个按钮：

| 状态 | 含义 |
|---|---|
| 未设置 | 平台默认——Win10 起通常走 TSC + 动态计时，多数平台这样最稳 |
| `true`（强制 HPET） | 计时源独立、抖动小；部分老 Intel 平台帧时间更稳，但延迟比 TSC 高 |
| `false` | 明确禁用 HPET |

- **强制 HPET** → `bcdedit /set {current} useplatformclock true`
- **恢复平台默认** → `bcdedit /deletevalue {current} useplatformclock`（本来就没有时视为成功）

没有实测对比就别动——这一项不是「越开越好」，两个方向都有人在用。

### 三、Hyper-V 关掉的代价是硬的

收益有争议（root hypervisor 会接管中断与计时，多一层虚拟化开销；老平台 + 竞技游戏有人测出帧时间更稳），代价很明确：

关掉之后 **WSL2 / Docker Desktop / Windows 沙盒 / Hyper-V 虚拟机 / 安卓子系统 / 内存完整性（内核隔离）全部不能用**。
如果开着「内存完整性」，系统可能直接拒绝关闭，要先去「Windows 安全中心 → 设备安全性」关掉它。

程序同时读 `DeviceGuard\EnableVirtualizationBasedSecurity` 和 `HVCI Enabled`，命中就在卡片上写明。

### 四、卓越性能：两个实测坑

1. **不需要管理员**——`PowerDuplicateScheme` / `PowerSetActiveScheme` 普通用户就能建方案、切方案（和 `powercfg -duplicatescheme` 一样）。
2. **非激活的方案会被藏起来**：复制出来的「卓越性能」在 `PowerEnumerate` 和 `powercfg /list` 里看不到，
   必须先 `SetActive` 一次才出现；一旦切走，又从列表里消失（`powercfg /query <GUID>` 仍能查到）。

所以程序不依赖枚举：**先扫 `HKLM\...\Power\User\PowerSchemes` 注册表按名字认，再退回记住的 GUID**。
切换时会记下「切换前的方案」，卡片上给「切回上一个方案」，不会把你原来的方案弄丢。

### 五、N 卡 Boost：为什么只生成 .nip

「电源管理模式 = 优先最高性能」存在 `ProgramData\NVIDIA Corporation\Drs\nvdrsdb0.bin` 里（二进制 DRS 库），
直接改等于让显卡驱动承担风险。所以生成 **NVIDIA Profile Inspector 的标准 .nip**：

- 字段 `Power management mode` = `0x1057EB71`，值 `1`（最高性能优先），写进 `Base Profile`（对所有程序生效）
- 导入后写的是同一份 DRS 数据，效果一致，随时能在控制面板改回「标准」
- 也可以走命令行：`--nvidia-boost`，生成后自动定位文件

代价：空闲也维持高频，待机温度 +5~15℃、风扇更响。笔记本不建议长期开。

### 六、游戏进程优先级

只提**正在运行的游戏**，不动系统进程——把 `csrss` / `dwm` 之类乱提优先级只会让输入更堵。

- 认法沿用 `GameProcessCatalog`：已知游戏进程名 → 安装路径特征
- 目标优先级是「高」，**明确不用「实时」**——那会把输入/音频线程饿死，反而更卡
- 只改进程调度优先级，不写注册表，退出游戏自动失效
- 被反作弊保护的进程可能拒绝修改，会逐个如实报出来

## 延迟实测：把「改完有没有降」变成可测的

「游戏与显示」→ **延迟实测**。这个窗口**只测不改**：不改注册表、不写服务、不需要管理员。
它解决的是这类工具最容易被质疑的一点——改了一堆设置，到底有没有用？

### 一、测什么、不测什么

| 测 | 不测 |
|---|---|
| 用户态线程 `Sleep(1)` 的**实际唤醒间隔分布**（平均 / P50 / P95 / P99 / 最大 / 大尖峰数） | 驱动级中断延迟的**归因**（不给「是哪个 .sys」的结论） |
| 系统计时器分辨率（`NtQueryTimerResolution`） | 鼠标到屏幕的端到端输入延迟、游戏帧延迟 |
| DPC / 中断占 CPU 的百分比（WMI 尽力而为，读不到就留空） | ISR 单次执行时长（只计数，不算时长） |
| **内核 DPC 单次执行时长**（ETW，需管理员，见第四节） | 内核函数级热点（那要用 WPA 看调用栈） |
| **进程 / 线程 / 句柄总量**（量化「停服务到底回收了多少」，见第五节） | — |

**内核 DPC 有，ISR 时长没有，模块归因也没有。**
LatencyMon 靠内核驱动采集 ISR/DPC 执行时长并归因到具体驱动；本程序用 ETW 的 NT Kernel Logger
拿到 **DPC 单次执行时长**（见第四节），但**不做模块归因**、**不报 ISR 时长**——
这两项要么依赖符号解析，要么依赖可靠的进出事件配对，做不好就会给出错误结论，所以不做。
需要完整的驱动级归因时，仍应使用 LatencyMon 或 Windows Performance Analyzer。

用户态那一路测的是调度抖动，是内核延迟的下游表现，可作代理指标但不能等同，
也不拿来宣称「DPC 延迟降低了多少微秒」。

选 `Sleep(1)` 的理由：它同时受计时器分辨率、DPC/中断抢占、后台负载影响，所有 Windows 都能跑，
不写系统状态，因此适合在改设置前后反复做对照。

### 二、单机实测就发现了一个反直觉的例子

某次自检采样：计时器分辨率读到 **0.600 ms**，但平均唤醒间隔是 **15.55 ms**（P99 16.40 ms）。
只看「分辨率」会以为系统延迟极低，实际唤醒仍被约 15.6 ms 的时钟滴答主导。
**这正是必须实测、不能只看参数的原因**。软件检测到这种不一致时会直接提示「请以本轮实测为准」。

### 三、对照实验怎么做

1. 选轮数与每轮时长。**默认 3 轮**——连跑多轮才能看出同条件下的噪声有多大，单轮连噪声都不知道。
2. 改任何设置**之前**测一批，**第一轮自动成为基线**，不用再手动点「设为基线」。
3. **一次只改一项**，在相同负载、相同电源状态下再测一批。
4. 比较两批的 **P99 中位数**，而不是任何单轮。

多轮真正的作用不是「取平均更准」，而是**反过来检验测量本身可不可信**：
同一条件、同一台机器上连跑 3 轮，如果 P99 极差就超过基线 P99 的 15%（下限 0.5 ms），
说明这台机器的抖动主要来自背景负载，此时「改完降到 0.1 ms」这类结论毫无意义——噪声比效应还大。
软件遇到这种情况会明说「本机单轮对照不可靠，请关掉下载/渲染后重测，或把轮数提到 5 轮」，
而不是硬给一个看起来像结论的数字。单轮时也会明确写「只跑了一轮，无法判断重复性」。

软件会自动拍下每轮实验时**哪些优化项处于生效状态**（读 `TweakCatalog` 全量状态），
两次之间如果变了多项，会明确写「无法把差异归因到任何单项」；计时器分辨率变了也会提示「两轮不同条件」。

判定刻意保守：P99 变化要超过「基线 P99 的 15% 与 0.5 ms 取较大者」才算数，
样本少于 30 直接判「样本不足」。即使判「复测更低」，也会同时写明
「单次对照不能证明因果，建议同负载重复 3 轮」。**软件不会说「优化有效」**。

实验记录存 `outputs/latency-experiments.json`，可导出 Markdown 表格留档。

### 四、内核 DPC / ISR：能测多深，测不到什么

窗口右上角的 **「内核 DPC/ISR」** 按钮会开一个 ETW 的 NT Kernel Logger 会话，
订阅 `EVENT_TRACE_FLAG_DPC | EVENT_TRACE_FLAG_INTERRUPT`，直接从内核事件里读 DPC 的单次执行时长
（`PERFINFO_DPC.Duration`，单位 100 ns，已换算成微秒）。

**这条路不需要装驱动**。ETW 的内核记录器是系统自带能力，只要管理员权限；
LatencyMon 装驱动是为了 ISR 归因、驱动名解析和 watchdog，不是拿到时长本身的必要条件。

三条硬限制，都写在界面上：

- **需要管理员**。普通权限下会明确拒绝并说明原因，不会返回 0 或空数据。
- **不做模块归因**。不给「是某个 .sys 干的」这种结论——那需要符号解析与地址区间匹配，做错了比不做好。
- **ISR 只计数不算时长**。PERFINFO 的 ISR 事件没有可靠的单次时长字段，强行配对进出事件在丢事件时会算出离谱值。

**本机实测情况（如实记录）**：本程序在这台机器上（i9-13980HX / Windows 11）调用 `StartTrace`
始终返回 **161（ERROR_BAD_PATHNAME）**。已逐项排除：结构大小 128 字节、字段偏移全部经
`Marshal.OffsetOf` 校验、`LogFileMode=0x100` 与 `LogFileNameOffset=0` 回读确认、`SeSystemProfilePrivilege`
已启用、会话未被占用。官方文档对该错误码只列了两种原因，两种都排除了。
`logman query -ets` 显示系统里同时存在**两个** `NT Kernel Logger` 会话（正常只能有一个），
因此判断为本机有机制（安全软件 / 反作弊组件 hook ETW，或组策略）阻止了内核跟踪会话。

所以这个功能的**代码是按官方 API 完整实现的，但在本机未跑通**。软件在这种情况下会显示
「内核记录器被本机环境拒绝」并给出排查方向，而不是给一个天书错误码或假装采到了数据。
排错入口：`破烂优化.exe --kernel-diag`（需管理员），会穷举参数组合并回读字段值。

### 五、停服务到底回收了多少：把「轻量」量出来

Atlas 那类项目的收益有一部分来自停服务、删组件。但「停掉几个服务让系统更轻」这句话，
只有量出来才算证据。每次采样结束时会记录四个数字：

| 指标 | 来源 | 怎么用 |
|---|---|---|
| 进程数 | `Process.GetProcesses()` | 停服务前后各存一次，差值就是真实减少量 |
| 线程总数 | 遍历各进程 `Threads.Count` | 同上；受保护进程读不到会跳过，不因此作废整项 |
| 句柄总数 | 遍历各进程 `HandleCount` | 同上。这是判断「瘦身」有没有实际效果最直接的一项 |
| 已提交内存 | `Win32_PerfFormattedData_PerfOS_Memory` | 同上 |

**这些是采样结束那一刻的快照，不是区间统计**。进程随时创建销毁，所以判读看趋势不看个位。
读不到的项留空显示「读不到」，不填估算值。

用法很直接：改服务配置之前测一轮记下数字，改完再测一轮，差值就是实际回收量。
如果句柄一个没少，那所谓「瘦身」只是心理作用——这句话现在可以被数据验证。

### 六、为它准备的「延迟与调度」分组

系统优化里新增第 9 组 **延迟与调度**（4 项），都是能静态表达、可还原的单变量项，
专门给对照实验当素材：

| 项 | 键 | 代价 |
|---|---|---|
| MMCSS 保留带宽降到 0 | `SystemResponsiveness` 20→0 | 后台转码/下载可能变慢，满载时音频可能爆音 |
| 游戏任务设为高调度优先级 | `Tasks\Games` 的 4 个值 | 后台任务响应变慢，只对被 MMCSS 识别的程序有效 |
| 取消前台锁定超时 | `ForegroundLockTimeout` 200000→0 | 个别后台程序更容易抢焦点 |
| 提高系统时钟中断优先级 | `IRQ8Priority` | **效果依赖平台和计时源**，现代机器多半测不出差异，只适合做单变量实验 |

每一项都写明「需实测」「别叠加测试」，没有做成「一键全开」。

### 五、参考过但明确没做的

| 来源做法 | 为什么不做 |
|---|---|
| 网卡级 `*RSS` / `TcpAckFrequency` / 中断节流 | 要按接口 GUID 逐个写，静态清单表达不了，误配会断网 |

> 原先这里还列着「CPU 停核 / C-State 不做」，这一版已经实现——
> 见上面的 **CPU 停核** 章节。当时拒绝的两个理由（跨版本不稳、功耗温度代价）
> 现在通过「只改当前方案 + 记原值可还原 + 界面显著提示代价」来处理，而不是回避功能。
| 常驻进程把计时器锁在 0.5 ms | 本程序不常驻；要长期锁定必须装开机自启服务，代价与收益不匹配 |
| 内核 ISR/DPC 时长采集 | 需要内核驱动或 ETW 会话，普通权限拿不到，不假装能拿 |

## 三类功能怎么分：延迟优化 / 系统优化 / 免重装精简

工具装多了最容易出的问题不是「功能不够」，而是**分不清哪个改动属于哪一类**，
于是把「关个遥测」当成「降延迟」，看不到效果就反复折腾。所以这一版把判据写死：

| 功能域 | 改的是什么 | 判据 | 典型入口 |
|---|---|---|---|
| **延迟优化** | **时序**：中断投递、线程调度、计时器分辨率、设备唤醒 | 改动会改变「事件发生到被处理」的时间分布，而不只是功能有无 | 延迟优化、延迟实测、CPU 停核 · C-State |
| **系统优化** | **行为**：服务是否运行、组件是否存在、隐私是否上传、界面怎么显示 | 影响「系统做什么」，不直接承诺时序变化 | 系统优化、系统调优、服务、免重装精简 |
| **免重装精简** | **系统里有什么**：预装应用、计划任务、可选功能 | 减少存在的组件，AtlasOS 镜像阶段做的那类事里运行时能做的部分 | 免重装精简 |

**几个容易归错类的例子**（软件里也单独列了）：

- 「关闭 SysMain」常被当延迟优化，其实是系统优化——省的是内存与后台磁盘活动，时序影响测不出来。
- 「关闭 Game Bar / GameDVR」两者都有：录制组件占用属系统优化，帧时间抖动属延迟优化。本软件归到延迟优化，因为可测的是抖动。
- 「CPU 停核 / C-State」属延迟优化：改变的是核心被唤醒的时序；功耗温度是代价，不影响归类。
- 「减少遥测服务」纯系统优化，对延迟没有可验证影响，别拿它当降延迟手段。

**三类功能完全独立**：每张卡片单独打开、每项单独开关、各有自己的备份文件，
不要求「先开这个才能用那个」。你可以只用延迟实测、完全不动系统优化，反过来也一样。

## 防护状态审查：不帮你关，帮你查是谁关的

「安全与取证」→ **防护状态审查**。这个功能的名字刻意不叫「Defender 开关」，
因为它做的事和「关掉防护」正好相反：**判断防护有没有被别人悄悄关掉**。

### 一、为什么不做「一键关闭」

市面上确实有工具能「一键关 Defender」。它们只能走三条路，本软件一条都不走：

| 路径 | 实际做法 | 为什么不走 |
|---|---|---|
| **官方开关** | 组策略 `DisableAntiSpyware`、`Set-MpPreference -DisableRealtimeMonitoring` | 消费版 Windows 从 1903 起忽略 `DisableAntiSpyware`；实时保护只能由用户在安全中心手动关，脚本改不动（篡改防护开着时） |
| **滥用系统机制** | 向 Windows 安全中心（WSC）注册一个**假杀软**，让 Defender 按「避免双杀软冲突」的逻辑自己退让。为绕过 PPL 校验，要把 DLL 注入微软签名的 `Taskmgr.exe` | 这是 ATT&CK **T1562.001（削弱防御）**，微软已把 DefendNot 一类工具按恶意软件查杀。这是攻击技术，不是功能 |
| **内核驱动 / 打补丁** | 装签名驱动或利用漏洞直接改内核结构 | 破坏系统完整性，且随每次 Windows 更新失效 |

第三条路本软件也不具备条件（单文件、无驱动、不签名）。
所以「别人能做」的真相是：**他们要么在滥用 WSC，要么在骗你**。

### 二、那做什么

读三处，交叉判断：

| 数据源 | 读什么 |
|---|---|
| `root\SecurityCenter2` 的 `AntiVirusProduct` | 安全中心里注册了哪些产品、每个产品的实时保护是开是关 |
| `root\Microsoft\Windows\Defender` 的 `MSFT_MpComputerStatus` | 防病毒总开关、实时保护、篡改防护、被动模式、签名年龄 |
| `MSFT_MpPreference` | 排除路径与排除进程（恶意软件常把自己加进排除项长期驻留） |

### 三、判定规则

| 条件 | 结论 | 为什么 |
|---|---|---|
| 安全中心读不到 | **无法判断** | wscsvc 被停用或系统被精简，不猜 |
| 一个安全产品都没注册 | **疑似被第三方关闭** | 正常 Windows 至少注册 Defender |
| Defender 关着，且没有第三方接管 | **疑似被第三方关闭** | 这是最危险的组合：看起来有安全中心，实际没有实时防护 |
| 被动模式开着，但没有第三方产品 | **疑似被第三方关闭** | 被动模式只在第三方杀软注册后才出现。开着却没产品，是假杀软注册被撤销后的残留——DefendNot 的典型痕迹 |
| Defender 关着，但有第三方实时保护 | 正常 | Windows 的标准设计，不是入侵 |
| 篡改防护关闭 / 签名过期 / 有排除项 | 削弱 | 逐条列出原因 |

判定逻辑抽成了纯函数 `Classify(...)`，自检里构造五种组合逐一验证——总不能真把本机 Defender 关掉来测。

### 四、本机实测

在这台机器上（i9-13980HX / Windows 11）：安全中心可读，注册产品 1 个（Defender），
防病毒与实时保护均开启，篡改防护开启，0 条排除项 → 结论「防护正常」。

### 五、边界

- **只读**。不提供任何修改入口，包括「打开」——那属于安全中心该管的事。
- 被动模式读 `AMRunningMode`，读不到再退回注册表 `ForcePassiveMode`，两者都失败显示「读不到」。
- 排除项需要管理员才能读全；读不到时显示为空并在结论里说明，不写成「没有排除项」。
- 窗口里有一个 **「为什么没有关闭按钮」** 的按钮，点开是上面那张表的完整版——
  这类说明不常驻版面，但你要找的时候必须在。

## 优化推论：26 条跨仓库结论，每条写清前提与限制

「系统优化」→ **优化推论**。这里**不改任何系统设置**，只把多个开源优化项目里反复出现的结论抽成条目。

每条固定五段 + 一个证据等级：

| 字段 | 为什么必须有 |
|---|---|
| **结论** | 一句话说清这条到底主张什么 |
| **前提** | 在什么条件下才成立（缺了这条，结论就变成万能话术） |
| **依据** | 来自哪个仓库/文档/实测，可追溯 |
| **适用场景** | 什么人、什么硬件、什么负载下值得做 |
| **限制** | 什么时候不成立、有什么代价、别怎么用 |
| **证据等级** | 官方文档 / 多源一致 / 社区经验 / **本机实测** |
| **证据规模** | 机制 / 单机实测（附具体机器）/ 多源一致 |

**证据等级和证据规模是两个维度，缺一个都会让人误用结论**：
等级回答「这条是怎么来的」，规模回答「它能推广到多远」。
比如 RigPolice 的停核数据是**实测**（等级高），但只在 i9-14900F + Win11 一台机器上做过（规模小）——
两个标签一起看，才知道「方向可参考、绝对值别照搬」。

规模标签只在结论基于测量时出现；讲机制的条目不显示规模（它本来就不适合用「规模」讨论）。
标「单机实测」的必须写明是哪台机器、什么量级（自检有断言守这条）。

**关于社区实测数据能不能参考**：能借方向，不能借数值。本软件引用 RigPolice 的三组数据
（停核唤醒 15.9→0.26 ms、MSI 中断例程 1.9→1.0 次、Sleep(1) 默认 15.2 ms）都标了单机来源。
拿它们当「我这台机器也能降这么多」的证据是不成立的——所以软件把测量能力做进产品里，
而不是把别人的数字抄成结论。这一条本身就是第 26 条推论。

当前的 26 条覆盖三块：延迟 13 条（HPET、动态滴答、MSI、IRQ8、停核、C-State、MMCSS、前台优先、
Game Bar、USB 节能、计时器误读、测量方法论、**别人的基准数据怎么读**）、系统 8 条（SysMain、遥测、网络限流、
VBS/HVCI、卓越性能）、精简 5 条（Atlas 到底做了什么、Appx 可逆性、计划任务、WinSxS、Defender/Edge）。

## CPU 停核 · C-State：可以做，但代价必须一起说

「游戏与显示」→ **CPU 停核**。通过电源方案里**隐藏的处理器设置**实现，不写 bcdedit、不碰驱动：

| 项 | 键 | 能做什么 |
|---|---|---|
| 核心停放 | `CPMINCORES` / `CPMAXCORES` | 两者设为 100% = 所有核心常开，关闭停核 |
| 处理器闲置（C-State） | `IDLEDISABLE` | 设为 1 = 核心不再进入深度空闲 |
| 性能提升模式 | `PERFBOOSTMODE` | **只读展示**：要按 CPU 代际判断，静态规则容易给错值 |

**GUID 不是凭记忆写的**：本机 `powercfg /query SCHEME_CURRENT 54533251-…` 实查过。
`CPMAXCORES` 的常见误写是 `ea062031-0e34-4ff1-966b-1e8c1f0a0aa1`，实为 `…-9b6d-eb1059334028`——
自检里有一条断言专门比对这两个值，防止有人「凭印象」改回去。

### 关于停核的推论（界面上也原样显示）

核心停放会让空闲核心进入停放状态，被调度时需要先唤醒——这是它可能拉高抖动的原因。
把最小/最大核心数都设为 100%，等于所有核心常开，可消除这部分唤醒延迟。**但结论有前提**：

1. 只有「调度器确实在使用停核」的机器才有收益。若 BIOS 已关停核，或 CPU 走硬件自主调频
   （Intel HWP / AMD CPPC），改电源项**可能不改变实际行为**；
2. 代价是空闲功耗与温度上升，笔记本续航明显变短；
3. 必须与 C-State、MMCSS 分开测，否则无法归因。

**本机实测就撞到了第 1 条**：这台机器交流下 `CPMINCORES` 已是 100（本来就没停核），
电池下是 4%。所以界面会在「交流/电池」不一致时**不显示「已应用」**，
避免用户以为插电和电池状态一致。

### 三条硬约束

- **只改当前生效的电源方案**，不动「平衡/高性能」模板本身；切方案即恢复。
- **改前把 AC/DC 原值一起记下来**（`core-parking-backup.json`），「还原」按记录写回，不猜默认值。
- **需要管理员**。普通权限下只读展示，不假装能改。

## 服务预设：批量禁用，但每一项都要看得见后果

「系统优化」→ **服务预设**。这是 AtlasOS 那类项目「批量禁用服务」的做法，改成了可以逐项确认、改前留底、随时还原的形式。

### 一、为什么不是「一键全禁」

服务之间有依赖链；同一个服务在不同用途的机器上价值相反——SysMain 在机械盘上是有效的预读，在 SSD 上才接近纯开销；Spooler 有打印机就不能停。一把全禁之后，出问题的人不知道该先恢复哪一个。

所以这里的设计是：

- 每项写清「禁用后会发生什么」，不只写服务名；
- 分 **可停 / 谨慎** 两档，谨慎项必须自己看说明再勾；
- **只改启动类型，不立即停止服务**——正在跑的东西被硬停会中断用户手上的活；
- 改前把原值写进 `outputs/service-preset-backup.json`，一个按钮全部还原；
- **没有全选按钮**。这类操作的风险集中在「用户不知道某一项会关掉什么」，全选正好把最后一道判断省掉了。

### 二、硬拦截：这些服务不提供禁用入口

`WinDefend`、`SecurityHealthService`、`wuauserv`、`BITS`、`CryptSvc`、`TrustedInstaller`、`RpcSs`、`DcomLaunch`、`Power`、`PlugPlay`、`EventLog`、`ProfSvc`、`gpsvc`、`Schedule`、`Winmgmt`、`mpssvc`、`BFE`、`SamSs` 等——写死在代码的保护名单里，**界面上连勾选框都不出现**。禁了它们系统会以难以排查的方式坏掉，或者直接失去安全更新。

自检里有断言守着：清单与保护名单不能有交集。

### 三、清单范围

只收「禁用后能说清后果、且不会让系统起不来」的 24 项，分布在遥测与诊断、推广与演示、Xbox、搜索与索引、远程与共享、外设六类。

**没收进来的**：大部分 Atlas 也禁的服务。它们要么依赖具体硬件（蓝牙、触摸），要么一旦出错很难定位。清单短一点、每项都说清楚，比列 80 项让人自己猜要好。

### 四、界面上的一个细节

应用前会弹确认框，把「你将禁用哪些」「其中几项标了谨慎」「哪几项被其他服务依赖」逐条列出来，而不是只问一句「确定吗」。

## 免重装精简：AtlasOS 能做的那部分，不重装也能做

「系统优化」→ **免重装精简**。

先说清为什么单独做这个：AtlasOS 官方 README **明确要求全新安装**，它的效果有一半来自改安装镜像。
不愿重装的用户以前只能两个选择：重装，或者什么都不做。这个窗口提供第三条路——
**把运行时能安全做、且能说清可逆性的那部分拆出来**。

### 一、能做的三类

| 类别 | 内容 | 可逆性 |
|---|---|---|
| 预装应用 | 常见预装/推广应用（3D 生成器、资讯、天气、纸牌、Clipchamp…） | **难恢复**：多数能从 Store 装回，部分已下架 |
| 计划任务 | CEIP、兼容性评估、错误上报等遥测任务 | **可恢复**：点「还原」即重新启用 |
| 运行时做不到 | 见下表，只说明、无按钮 | — |

### 二、明确做不到的四项（不假装能删）

| 项目 | 为什么运行时做不到 |
|---|---|
| 删除 WinSxS 组件 | 只能清理「被新版本取代」的副本；任意删组件会导致更新失败且不可回滚 |
| 彻底移除 Edge | 与 WebView2、系统帮助深度绑定，删了会破坏依赖它的程序，更新还会装回 |
| 移除 Defender | 受篡改防护保护，强制关闭会被系统恢复，且让机器无防护。**本软件不提供任何关闭按钮** |
| 精简安装镜像 | 属于部署阶段（离线改 WIM/ESD），安装好的系统改不了 |

### 三、Atlas 还会停一批服务——这件事怎么处理

会。Atlas 那类项目除了删组件，还会把一批服务改成禁用（SysMain、诊断跟踪、搜索索引、部分遥测与
远程协助相关服务）。**停服务确实会让进程数、线程数、句柄数下降**，这是可测量的收益。

本软件**不提供「按 Atlas 清单批量禁用服务」**，理由很具体：

- 服务之间有依赖链。比如禁用某个基础服务会连带让依赖它的服务起不来，而这条链在不同 Windows 版本上不一样。
- 同一个服务在不同用途的机器上价值相反。SysMain 在机械盘上是有用的预读，在 SSD 上才接近纯开销。
- 批量禁用之后，出问题时用户不知道该先恢复哪一个。

取而代之的是两件可操作的东西：

1. **「服务」窗口**：逐项改启动类型、启停、看依赖与失败动作。一次只动一个，改动可回滚。
2. **「延迟实测」的负载量化**：采样时自动记录进程 / 线程 / 句柄 / 已提交内存。
   停服务前存一次、停完再存一次，差值就是实际回收量——**如果句柄一个没少，那这次「瘦身」就是心理作用**。

这也顺带回答了一个常见疑问：「优化完感觉快了」很难证伪，但「句柄从 117,921 降到 96,300」
是可核对的数字。软件只负责量，不负责替你说「快了」。

### 四、两个「不做」比「做」更重要

**不做「一键全选」**。预装应用卸载是不可逆性较高的操作，默认全不勾、逐项确认是底线。

**不做运行时依赖包**。本机实测：可移除包列表里混着 `WinAppRuntime`、`DDLM`、`VCLibs`、`UI.Xaml`
这类运行时依赖，删了会让依赖它们的应用起不来。程序在扫描阶段就排除，并把排除数量告诉用户。
自检里有两条断言守着：运行时包必须被识别、常见预装不能被误判成运行时包。

### 五、安全约束

所有 shell 命令的参数都来自**内置白名单或严格校验**，绝不把扫描到的包名直接拼进命令行。
任务路径必须匹配 `\Microsoft\…`，包名只用于在已枚举对象里精确匹配，脚本通过 base64 传入。

## 脚本复用评估：哪些能直接搬，哪些只能借结论

做这一版之前，先把「已有脚本能不能直接复用」盘了一遍。结论是：**开发脚本能直接复用，
外部优化脚本几乎都不能直接搬**——原因不是技术，而是语言与许可证。

### 一、本仓库自带的脚本（直接复用 / 小幅修改）

| 脚本 | 用途 | 复用方式 | 选择理由 |
|---|---|---|---|
| `pack.ps1` | 构建 + IL 字符串加密 + 单文件打包 | **直接使用**，未改动 | 已验证可用：先 build、再混淆、`--no-build` 发布才能把加密后的 DLL 打进单文件 |
| `build.cmd` | 双击调用 `pack.ps1` | **直接使用** | 只是入口包装 |
| `save.cmd` | 本地 git 提交辅助 | **直接使用** | 提交信息由人填，不自动化 |
| `发布公告.cmd` | 改完公告后重新签名并打开仓库页 | **直接使用** | 调用软件自身的 `--sign-notice`，签名逻辑在 C# 里，脚本只是壳 |
| `tools/shot.py` | 启动程序 → 找窗口 → PrintWindow 截图 → 白屏检测回退 | **小幅修改**：新增 `--wheel=N` 参数 | 原本只能截首屏，长列表截不到下半部分。加 `--wheel` 后可以滚动到目标区域再截，验收「分组/列表」时必需。**只改了截图工具，没进产品** |

## 构建

**双击项目根目录的 `build.cmd` 就行**，它调 `pack.ps1`，做四件事：构建 → 字符串加密 → 打单文件 → 清中间文件。

```
build.cmd → pack.ps1
  [1/5] dotnet build（Release / win-x64 / 自包含）
  [2/5] Obfuscar 加密字符串常量（只动字符串，不动名字）
  [3/5] dotnet publish --no-build 打单文件（复用已加密的 dll）
  [4/5] 复制到 破烂优化.exe
  [5/5] 删除 dist-standalone / .tmp-obf
```

`--no-build` 是关键：`dotnet publish` 默认会重新编译，把加密过的 dll 覆盖掉；
加了这个参数它才会直接拿 `bin` 里那份加密产物打包。

手动等价命令：

```bash
dotnet build src/SysDiag/SysDiag.csproj -c Release -r win-x64 --self-contained true -p:DebugType=none
obfuscar.console.exe tools/obfuscar.xml          # 输出到 .tmp-obf
cp .tmp-obf/SysDiag.dll src/SysDiag/bin/Release/net8.0-windows/win-x64/
dotnet publish src/SysDiag/SysDiag.csproj -c Release -r win-x64 --self-contained true \
  -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true \
  -p:EnableCompressionInSingleFile=true -p:DebugType=none --no-build -o dist-standalone
cp dist-standalone/SysDiag.exe 破烂优化.exe
```

两个 publish 参数不能省：

- `IncludeNativeLibrariesForSelfExtract=true`——`WebView2Loader.dll` 是原生库，不设它单文件会把 WebView2 弄坏
- `EnableCompressionInSingleFile=true`——不加这个体积会从 64.3 MB 涨到约 150 MB

> 发布前先关掉正在运行的 `破烂优化.exe`，否则复制会失败（文件被占用）。脚本已处理：删不掉就改名挪开再复制。

第一次在新机器上构建，需要装混淆工具：`dotnet tool install -g Obfuscar.GlobalTool`。

## 版本管理：改坏了怎么退回去

项目根有一个 **本地 git 仓库**——只在你这台机器上，不联网、不上传，纯粹当"存档点"用。

### 日常：改完就存一次

**双击 `save.cmd`**，它会：

```
1. 列出改了什么（git status --short）
2. 问一句说明（直接回车 = update）
3. 存档（commit）
4. 打印最近 5 次存档
```

不用记任何命令。等价的命令就是 `git add -A` + `git commit -m "说明"`。

### 命令速查

| 想做的事 | 命令 |
|---|---|
| 看改了什么文件 | `git status` |
| 看具体改了哪几行 | `git diff` |
| 存档 | `git add -A` 然后 `git commit -m "说明"` |
| 看历史 | `git log --oneline` |
| 看某次改了啥 | `git show <提交号>` |
| 看某个文件的历史 | `git log -p -- README.md` |
| **改坏了，丢掉没存档的改动** | `git restore .` |
| **整个项目回到某个旧版本** | `git reset --hard <提交号>` |
| 撤销刚存的这次，但保留改动 | `git reset --soft HEAD~1` |

**两条会真的丢代码**，用之前先确认：

- `git restore .` 丢掉所有未提交的修改，找不回来
- `git reset --hard` 直接把工作区改回旧版本

正确姿势永远是：**先 `save.cmd` 存一次，再回滚**。有了存档，回滚就只是"换个地方继续"，不是"赌一把"。

### 什么进仓库，什么不进

`.gitignore` 已排除：`bin/` `obj/` `dist-standalone/` `stage*/` `.tmp-obf/` `outputs/` `*.exe` `keys/`

- 源码、XAML、README、`build.cmd`、`pack.ps1`、`tools/` —— 全部入库（270+ 个文件）
- 64 MB 的 exe —— 不入库。每次都能重新构建，进仓库只会让历史迅速臃肿
- `keys/notice-private.pem`（公告签名私钥）—— **绝不能入库**，已在 `.gitignore` 里

> 私钥一旦提交过，即使后来删掉，历史记录里仍然存在。所以不要对它用 `git add -f`。

### 以后想推到 GitHub

现在不需要。真要推，先建**私有**仓库再：

```bash
git remote add origin git@github.com:wancatnap/仓库名.git
git push -u origin main
```

## 防逆向：做了什么，以及做到哪一步

### 一、先认清底线

.NET 程序**不存在真正的「加密」**。IL 天生可反编译，任何手段都是外面套一层，运行时必然还原。
所以这里的目标不是「让逆向不可能」，而是「把成本从 5 分钟抬到几天」。

实测（`ilspycmd` 对本仓库发布产物）：

| 状态 | 可读字符串字面量 | 中文关键词 | 反编译后看到的机器码算法 |
|---|---|---|---|
| 加密前 | 7,145 处 | 全文可见 | `("SMBIOS UUID", true)` |
| 加密后 | 298 处 | 0 处 | `(4B426D24-…-A7D1.aGH(), true)` |

### 二、现在做了什么：只加密字符串，不动名字

`tools/obfuscar.xml` 里 `HideStrings=true`，其余 rename 全部关掉。

**还有一处容易被漏掉**：`const string` 会进元数据常量表，`ldstr` 加密碰不到它。
本项目里 `SigmaRules.Builtin`（约 50 KB 的检测规则全文）原本就是 `const`，
反编译一眼能读完；改成 `static readonly` 后才落进方法体被加密。
`CleanerRules.BuiltinIni`、`HtmlDoc.Css` 同理。

**为什么不动名字**：这是 WPF 程序，XAML 的 `x:Class`、绑定路径、枚举的 `ToString()`、
JSON 序列化字段名、以及 496 项自检里的按名字查找，全都依赖类型名和方法名。
名称一改会导致成片功能失效，收益远小于维护成本——**只加密字符串是收益/风险比最高的做法**。

加密后依然能正常工作，因为解密出的值与原文完全一致（`case "x"`、`switch`、
`Enum.Parse`、反射按名查找全部不受影响）。实测 496 项自检全过。

### 三、还没做的，以及为什么

| 手段 | 状态 | 原因 |
|---|---|---|
| 名称混淆 | **不做** | WPF + 大量反射，改了就崩 |
| 核心逻辑原生化（NativeAOT DLL） | **没做** | 本机没有 MSVC / Windows SDK / Rust，装工具链要 2–4 GB |
| 整程序 NativeAOT | **不可能** | .NET 8 的 WPF **不支持 NativeAOT**，这是硬限制（Avalonia / WinUI3 才行） |
| 商业壳（.NET Reactor / Themida） | 没上 | 要付费；且和单文件自包含有兼容风险 |
| 服务端授权 | 没做 | 需要服务器，且要先确认是不是商业化分发 |

### 四、还想往上加的话，按这个顺序

1. **装 VS Build Tools（含 C++ 与 Windows SDK）**，把机器码算法、Sigma 匹配、自检规则
   抽成 `PublishAot=true` 的独立类库，主程序 P/Invoke 调用。逆向者只能看汇编。
2. **加自校验**：启动时核对自身哈希。注意单文件是压缩的，改不了包内字节，
   所以期望值要放在外部（服务端或注册表），不能内嵌到同一个 exe 里。
3. **服务端授权**：校验放服务器，客户端只持有 token。这是唯一能真正防「patch 掉限制」的做法。

> 一句话：**想防抄，做原生化；想防盗版，做服务端；只做客户端加密，都只是抬门槛。**

## 远程公告（签名 JSON，不做授权）

主窗口顶部可以显示一条远程公告。**只做公告，不做任何「禁用软件」的逻辑。**

### 一、为什么不是腾讯文档

一开始考虑过「公告写在腾讯文档里，客户端读外链」，实测不可行：

1. 腾讯文档分享页是 Canvas / SPA 渲染，纯 HTTP GET 只拿到 JS 壳，正文不在 HTML 里。
2. 内容接口（`/openapi/...` 或内部 `/cgi-bin/...`）一律要 OAuth Token 或登录 Cookie。
3. 把 Token 内嵌进客户端 = 把钥匙发给每个用户，而且 Token 会过期、会被风控。

所以腾讯文档只当「编辑界面」，真正的分发走**公开仓库里的静态 JSON**。

### 二、链路

```
编辑 notice-source.json（明文）
   ↓  SysDiag.exe --sign-notice notice-source.json notice.json
带签名的 notice.json
   ↓  上传到 GitHub（公开仓库）
客户端 HTTPS GET → 验签 → 缓存 → 失败降级
```

客户端地址（改仓库只需改一行）：`RemoteNoticeService.DefaultUrl`

### 三、必须验签

JSON 放在公开仓库里，谁都能看、谁都能 fork。**没有签名就等于没有防线**——中间人、被劫持的 DNS、甚至一个改过的 hosts，都能返回任意内容。

所以每条公告都带 ECDSA P-256 签名：

- 签名覆盖固定顺序的规范串：`v|enabled|level|title|message|url|urlText|expires|signedAt`
- 字段里出现 `|` 直接判不合法（否则规范串有歧义）
- 公钥硬编码在 `RemoteNoticeService.PublicKeyBase64`；**私钥只在开发机 `keys/notice-private.pem`，不进仓库、不打包**
- 缓存文件读回来也要**重新验签**——本地文件同样可能被改

### 四、失败一律降级

| 情况 | 行为 |
|---|---|
| 网络失败 / 404 | 用本地缓存（7 天内） |
| 缓存也没有 | 整条公告不显示，不占位、不弹窗 |
| 验签失败 | **不显示**，并记下原因 |
| 内容过期 / `enabled=false` | 不显示 |
| 用户点过「关闭」 | 记住签名，同一条不再出现 |

实测：仓库不存在时 0.7 秒失败、界面无任何提示、启动不受影响。

### 五、怎么发一条公告

```bash
# 1. 改文案（不要出现竖线 |）
notepad notice-source.json

# 2. 签名（会自验一遍，失败会报出来）
破烂优化.exe --sign-notice notice-source.json notice.json

# 3. 把 notice.json 传到仓库，覆盖同名文件
# 4. 验证远端（可选）
破烂优化.exe --notice-probe
```

首次使用要生成一对密钥（私钥留在本机）：

```bash
破烂优化.exe --gen-notice-key
# 输出里的 Base64 填到 RemoteNoticeService.PublicKeyBase64，然后重新编译
```

### 六、「查看详情」打开的是功能一览

公告条右侧那个按钮**不再跳浏览器**，而是弹一个内置窗口：把主界面 9 组 75 张卡片摊平成一页清单，
每条写「功能名 + 它解决什么问题」。公告里提到的原文链接放在弹窗底部，需要时再点。

这么改的理由：用户看到「更新了什么」之后，下一个问题通常是「这软件到底能干什么」。
跳浏览器等于把他扔出软件；摊开一页清单，答案就在眼前。

清单数据直接读 `CardCatalog`，**不另维护一份文案**——否则哪天加了功能，这里就是过期信息。
弹窗顶部有搜索框，73 项里找某个能力不用翻。

### 七、边界

- **不做授权**。远程开关一旦出错，用户会以为软件坏了——真要控制可用性，得走服务端签发 token，不是读一个 JSON。
- **公告不是实时推送**：只在启动时拉一次，缓存 7 天。
- 仓库必须是**公开**的；私有仓库的 raw 需要 token，内嵌 token 等于泄露。

## 程序外观：图标与名称

任务管理器里显示的「描述」来自 exe 的版本资源（AssemblyTitle / Product），图标来自 `<ApplicationIcon>`。
这一轮把两处都补齐了，之前的状态是：**名称还写着旧名「系统诊断台」，图标是 .NET 默认图标**。

| 显示位置 | 数据来源 | 说明 |
|---|---|---|
| 任务管理器「描述」列 | 版本资源（AssemblyTitle/Product） | 旧的 AssemblyInfo 缓存在 `obj/` 里，改名后必须清 obj 重新打包，否则 exe 里还是旧字符串 |
| 任务管理器 / 资源管理器图标 | `<ApplicationIcon>` 写进 PE 的图标资源 | 由 `tools/make-ico.py` 生成（纯 Python 画像素，16~256 七档，改配色重跑即可） |
| 任务栏 / 窗口图标 | WPF 窗口的 `Icon` 属性 | **WPF 窗口不设置 Icon 时，任务栏显示系统默认图标，不会自动用 exe 图标**——所以除了 exe 图标，MainWindow 还要显式 `Icon="pack://application:,,,/app.ico"` |

自检守着这两处：`打包：任务管理器显示的名称不是旧名`（读 exe 的 FileVersionInfo 对比）与
`打包：exe 内嵌了自定义图标`（枚举 PE 的 RT_GROUP_ICON 资源；不能只用 ExtractIcon 判断——
exe 没图标时它会返回系统默认图标，句柄照样非 0）。

## 自检：496 项，全部在软件内跑

```bash

```
