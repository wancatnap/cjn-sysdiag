# 系统诊断台 · 功能深化与报告导入方案

> 版本：草案 v1（2026-11-06）
> 目的：把现有 56 张卡与 GitHub 同类项目对齐，指出可深入的点，并设计「报告导出 + 导入」的闭环。
> 原则：**不破坏单文件绿色特性**；**新增入口不超过 2 处**；**宁可少做，不做会误判的功能**。

## 二、GitHub 对照（按功能域，不逐卡）

### 1. 日志与事件（日志分析、Sigma、事件日志）

| 项目 | 语言 / 许可 | 它强在哪 | 我们的差距 |
|---|---|---|---|
| **Chainsaw** `WithSecureLabs/chainsaw` | Rust / GPL-3.0 | evtx 二进制直读 + Sigma 全量规则 + 关键词/字段搜索 | 我们走 EventLogReader，只能读本机活动日志；不支持导出 evtx 文件 |
| **Hayabusa** `Yamato-Security/hayabusa` | Rust / AGPL-3.0 | 多线程扫 GB 级 evtx，输出 CSV/JSON 时间线 + HTML 告警报告，内置数千条 Sigma | 我们没有统一时间线，规则只有 22 条 |
| **EvtxECmd**（EZ Tools） | C# / MIT | 每条 evtx 记录转结构化字段 + map 文件做字段归一 | 我们的字段提取是硬编码的，换通道要改代码 |
| **SigmaHQ/sigma** | YAML | 规则生态 | 我们只取了 22 条自写规则 |

### 2. 进程 / 注入 / 内核

| 项目 | 语言 / 许可 | 它强在哪 | 我们为什么不照抄 |
|---|---|---|---|

| **System Informer** `winsiderss/systeminformer` | C / MIT | 句柄粒度最细：谁以什么权限打开了目标进程 | 纯手工排查界面，无结论 |
| **OpenArk** `BlackINT3/OpenArk` | C++/Qt / LGPL-2.1 | 内核回调、过滤驱动、IDT/SSDT | 要装驱动，与单文件定位冲突 |

## 三、可深入的点（按投入产出排序）

| # | 方向 | 借鉴 | 收益 | 成本 | 风险 | 建议 |
|---|---|---|---|---|---|---|
| 1 | **报告结构化 + 导出/导入 + 双份对比** | 无直接对应（自研） | 极高：形成闭环，支持"用户发报告→客服复核" | 中 | 低 | **立即做** |
| 2 | **统一时间线**（Sigma / USN / 驱动 / PnP 合成一条） | Velociraptor、Hayabusa | 高：从"一堆列表"变成"一条故事线" | 中 | 低 | 做 |
| 3 | **Prefetch + ShimCache 解析** | PECmd、AppCompatCacheParser | 高：补上"程序运行过"的另一半证据 | 中 | 中（格式随版本变） | 做 |
| 4 | **句柄维度**（谁在读游戏进程） | System Informer | 高：最贴近外挂行为 | 中 | 中（需管理员，误报需白名单） | 选做（B 档） |
| 5 | **$MFT 解析**（文件名/时间戳/ADS） | MFTECmd | 中：时间线更完整 | 高（NTFS 结构 + 权限） | 高（解析错会给出错误时间） | 缓 |
| 6 | **磁盘 treemap** | WinDirStat | 中：直观 | 中（自绘控件） | 低 | 缓 |
| 7 | **规则库可更新** | SigmaHQ | 中：不用发版就能加规则 | 高（字段映射 + 误报治理） | 高 | 不做（内置更可控） |
| 8 | **内存比对（pe-sieve 思路）** | pe-sieve | 高 | 极高 | 极高（误报、性能、反作弊冲突） | 不做 |

**结论**：真正值得排期的是 1 → 2 → 3，第 4 项看是否需要"客服判挂"场景。

## 四、报告导出 / 导入设计（本次重点）

### 4.1 现状

- 报告是**单份 HTML**，样式内嵌，只读。
- `ReportPayload` 只有 `HtmlPath` + `PlainSummary`，**没有结构化数据**。
- 想二次利用（对比、统计、导入）只能人眼看 HTML。

### 4.2 设计目标

1. 一份报告 = **一个可分发文件**，对方双击能看，我们也能重新读进来。
2. 导入后能**与本机现状对比**，也能**与另一份报告对比**。
3. 不引入数据库、不联网、不依赖外部程序。

### 4.3 文件格式：`.sdreport`（zip）

```
报告名-20261106-1120.sdreport
├── report.json       结构化数据（唯一可信源）
├── report.html       人类可读版（可选，缺失时由 json 重建）
├── manifest.json     文件清单 + 每个文件的 SHA256 + 工具版本
└── evidence/         可选：原始数据（CSV/JSON），如 USB 清单、Sigma 命中
```

**为什么用 zip 而不是单 JSON**：报告要能直接发给不懂技术的人，双击解压就能看 HTML；同时保留机器可读的 JSON。

**为什么不只发 HTML**：HTML 里的信息要靠正则抠，样式一改就崩，且无法表达数值与结构。

### 4.4 report.json 结构

```json
{
  "schema": "sysdiag.report/1",
  "kind": "cheat-scan",
  "generatedAt": "2026-11-06T11:20:00+08:00",
  "tool": { "name": "系统诊断台", "version": "3.7" },
  "machine": {
    "name": "DESKTOP-XXXX",
    "user": "sample-user",
    "os": "Windows 11 26100",
    "admin": false
  },
  "verdict": {
    "score": 7,
    "level": "低",
    "text": "未发现组合线索，有 6 条提示项",
    "counts": { "warn": 0, "hint": 6, "ok": 7 }
  },
  "sections": [
    {
      "group": "日志规则匹配",
      "items": [
        {
          "level": "hint",
          "title": "服务注册了内核驱动",
          "detail": "服务加载 .sys 文件……",
          "basis": "8 次 · 最近 11-05 20:47:12",
          "weight": 3,
          "tags": ["腾讯 ACE"]
        }
      ]
    }
  ],
  "stages": [{ "name": "模块完整性", "state": "done", "items": 3120, "note": "…" }],
  "timeline": [{ "time": "2026-11-05T20:47:12", "source": "删除", "text": "x.exe", "level": "hint" }],
  "hashes": { "report.html": "sha256:…", "evidence/usb.csv": "sha256:…" }
}
```

设计要点：
- `schema` 带版本号，导入时先校验；不匹配则提示但尝试读取（只取认识的字段）。
- `kind` 决定用哪个渲染器与对比器。
- `sections/items` 是通用结构，所有报告都能塞进来（Sigma 命中、体检发现、清理清单都能映射）。
- `machine.admin` 记录生成时是否管理员——直接影响「受限」项的解释。

### 4.5 导出入口（1 处，不加卡）

**报告窗口工具栏**加一个按钮：

```
[重新加载] [浏览器打开] [复制摘要] [导出报告包] [打开所在目录] [关闭]
```

点击 → 保存对话框（默认到 `outputs\`，文件名 = 报告标题 + 时间戳）→ 生成 zip → 完成后提示「已导出，可直接发给别人」。

同时**所有生成报告的地方**（体检、Sigma、清理、USN、证据包、日志分析）自动走高亮路径：只要走 `ReportPayload` 就带上 `Structured` 字段。

### 4.6 导入入口（1 处，加 1 张卡）

主界面「常用目录」组上方加一张卡：

**「报告对比」**（`报告导入·双份对比`）

窗口逻辑：
1. 工具栏：`[选择报告…]` `[清空]`
2. 拖拽 `.sdreport` 到窗口也能导入
3. 导入后显示：报告标题、机器名、生成时间、结论、条目数
4. 再导入第二份 → 自动进入**对比模式**：

```
              基准（A）        对比（B）        变化
风险分          7                25             ↑ 18 恶化
线索            0                1              +1
模块完整性      正常              2 个异常       恶化
反作弊组件      腾讯 ACE         腾讯 ACE        —
```

对比规则（可解释）：
- 以 `group + title` 为键
- 状态变化：`ok→hint/warn` = 恶化；`warn→ok` = 改善；只在 A 出现 = 消失；只在 B 出现 = 新增
- 数值变化：score / counts 直接相减
- 输出「变化摘要」+ 可导出对比报告（同样走 `.sdreport`）

### 4.7 安全边界（必须写进代码）

| 风险 | 处置 |
|---|---|
| 导入的 zip 含 `..\..\` 路径穿越 | 解压前校验每个 entry 的规范化路径必须在目标目录内 |
| zip 炸弹（解压后超大） | 限制解压总量 ≤ 200 MB、单文件 ≤ 50 MB、entry 数 ≤ 200 |
| HTML 内嵌脚本 | 渲染前剥离 `<script>`；WebView2 关闭脚本执行 |
| 伪造报告 | `manifest.json` 带 SHA256，界面显示「完整性：通过/不一致」，不阻止打开但明确标注 |
| 版本不兼容 | `schema` 主版本不同 → 只读展示，禁用对比 |

### 4.8 兼容与迁移

- 现有 HTML 报告**保持原样**，不破坏。
- 新报告同时产出 HTML + JSON；旧报告无法导入（提示「这份报告是旧格式，只能查看」）。
- 版本号写在 `tool.version` 与 `schema` 两处，便于排查。

## 五、分期计划

### P1：报告闭环（建议先做）
1. `ReportPayload` 加 `ReportData`（结构化对象）
2. 体检 / Sigma / 清理 / USN 四类报告填充结构化数据
3. 报告窗口加「导出报告包」
4. 新增「报告对比」窗口：导入 1 份查看、2 份对比、导出对比结果
5. 自检：序列化往返、schema 校验、zip 安全校验（路径穿越 / 超限）、对比算法

**验收**：导出→删掉原 HTML→导入→内容一致；改一条数据→对比能标出恶化。

### P2：统一时间线
- 把 Sigma 命中、USN 删除、驱动安装、PnP 事件合并成一条按时间排序的列表
- 在体检窗口加「时间线」页签，报告里出一节
- 借鉴 Hayabusa 的「一条时间线回答发生了什么」

### P3：Prefetch + ShimCache 解析
- Prefetch：解析 `.pf`（版本 30/31，含压缩），取运行次数、最后运行时间、引用文件
- ShimCache：读 `AppCompatCache`，补"存在过但可能没运行"的证据
- 两者都只读，不需要驱动

### P4（选做）：句柄维度
- `NtQuerySystemInformation(SystemExtendedHandleInformation)` 枚举句柄
- 找「非系统进程对游戏进程持有 PROCESS_VM_READ/WRITE」
- 白名单：反作弊、录屏、加速器、GPU 驱动
- 只作提示，不作线索

## 六、不做什么（写下来避免反复讨论）

1. **不加内核驱动**：破坏单文件绿色、与反作弊冲突、蓝屏风险。
2. **不做内存 dump 比对**：误报与性能代价远超收益。
3. **不做规则库在线更新**：字段映射与误报治理成本高，内置更可控。
4. **不做联网上报**：报告只在本机流转，避免隐私与合规问题。

---

## 七、需要确认的三件事

1. 导入后的主要用途是「自己复核」还是「客服判挂」？后者需要更强的对比与结论措辞。
2. 导出格式是 `.sdreport`（zip，含 HTML+JSON）还是单 JSON？前者对外友好，后者对程序友好。
3. 是否允许导入**他人发来**的报告？允许则必须启用完整性与脚本剥离，且界面要显式标注来源。
